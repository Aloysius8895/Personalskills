# 代理写代码之后：验证与长期维护

本 skill 合并了两场 AI Engineer 演讲：
- **A 部分**来自 Duolingo 的演讲（下述）。
- **B 部分**来自 Dmitry Buykin（标题署名 Maersk）的 [Agents Made Code Free. Maintaining It Didn't Get Cheaper.](https://www.youtube.com/watch?v=oeknLUsN_GE)（18:04）。

两者的共同前提：代理让写代码变便宜，瓶颈转到**验证**和**人的注意力**。A 解决「怎样让代理产出的改动可被验证、可被人放心批准」，B 解决「代理持续改动下，系统怎样不越长越乱」。只需要其中一件事时，只执行对应部分。

# A 部分：用编码代理批量补写单元测试

来源：Duolingo 的 Kush（标题署名 Kush Agrawal）在 AI Engineer 的演讲 [225,000 Lines of Tests, Written and Merged by Agents](https://www.youtube.com/watch?v=D_4Rn6uLdQM)（12:38）。依据为英文自动字幕，**未核验画面**。时间戳为字幕时间。下文的数字是讲者在 Duolingo iOS 上报的结果，不是保证值；标「可采用」的是整理时补充的建议。

## 什么时候用

- 代码库覆盖率低，想用编码代理批量补测试，但每个 PR 仍要人审批。
- 已有一类「形状相同」的批量改造任务（迁移架构、换异步框架、补 snapshot test），想复用同一闭环（讲者 11:36 起提到 Duolingo 已这样用）。

不适合：没有 CI、没有覆盖率报告、或团队不愿审代理 PR 的仓库，先补这些前置条件。

## 需要的输入

| 输入 | 说明 |
|---|---|
| 目标仓库与语言/测试框架 | 例：iOS + XCTest/Swift Testing；Android + JUnit；Python + pytest |
| 可测切片 | 架构上最容易测的部分（Duolingo 只做 MVVM 的 view model / repository / data source，跳过 UI） |
| 覆盖率报告来源 | 每次合并到主分支自动生成并存到共享位置 |
| 编码代理 | 能在云端/CI 运行的代理（他们用 Claude Code） |
| 编排引擎 | 支持定时、子流程、重试、超时、幂等（他们用 Temporal；可采用其他 durable workflow 引擎或 CI 定时任务） |
| 代码托管 | 支持 label、PR、auto-merge、Actions 的平台（他们用 GitHub） |
| 可观测 | 能看每次代理运行的状态与成本（他们用 Datadog） |

## 核心循环

`identify → write → verify → resolve → iterate`（2:28）：选文件 → 代理写测试 → CI 与质量验证 → 人审合并 → 把拒绝理由回写进 prompt 和 skill。

## 步骤

### 1. 记录基线，圈定切片
- 记录整体覆盖率和各层覆盖率（Duolingo 起点：整体 11%，MVVM 约 9%，0:01–1:43）。
- 只选最好测的切片作为第一阶段范围。
- 成功标准：有一份写明范围和基线数字的文档。

### 2. 本地小批验证（4:03–5:19）
- 用一个代理命令当编排者：生成覆盖率报告 → 用脚本选文件 → 每个文件派一个子代理写测试、一个子代理开 PR。
- 分小批跑（他们两批：17 个合并 8 个，40 个合并 19 个）。**目标是收集失败模式，不是追求合并数。**
- 把每种失败写进仓库里的 testing skill / 规则文件。讲者遇到的例子：
  - 同一文件混用两种测试框架 → 写明何时用哪种；
  - 难以 mock 的具体类单例 → 改代码库为协议/接口版本，再加 lint 强制；
  - 并发和依赖时间的测试导致 flaky → 在 skill 里补规则与示例。
- 成功标准：主要失败模式都有对应规则或代码改造。

### 3. 建立覆盖率的唯一来源
- 每次合并到主分支触发一个 CI job，生成覆盖率报告并上传共享存储（他们用 S3，5:21 起）。

### 4. 写 selector 打分（5:21–7:21）
- 给每个源文件打「代理有多大把握写好测试」的分：
  - 目标文件类型加权（他们给 view model / repository / data source **2.5 倍**）；
  - 遗留代码降权；
  - UI 暂时跳过（更适合 snapshot test）；
  - 大文件扣分。
- 成功标准：每批选出的文件以高把握度文件为主。

### 5. 定时 backfill，并行写测试
- 定时任务拉最新覆盖率 → selector 选一批 → 每个文件一个子流程并行执行。
- 代理每次：克隆仓库 → 读仓库内 testing skill → 只写测试和必要的 mock/fake → 开 PR。
- PR 打统一 label（他们用 generated test），描述用统一模板并**写明 AI 生成**。
- 审阅人有四个选项：批准即自动合并、直接 push 修改、改派、关闭并写理由。
- 利用编排引擎的幂等，保证同一文件不会被重复开工。

### 6. PR 生命周期状态机（7:21–8:40）
每隔几小时巡检所有带该 label 的开着的 PR，**每个 PR 每轮只做一个动作**：

| 状态 | 动作 |
|---|---|
| 有冲突，或已开约 3 周 | 关闭，标 stale |
| CI 运行中，或已有审阅人 | 跳过 |
| CI 绿且无审阅人 | 用 `git blame` 找被测源文件主要贡献者，指派并开 auto-merge |
| CI 红 | 进入修复（见下） |
| 被审阅人拒绝 | 该文件冷却 30 天 |

CI 修复分层：pre-commit / lint 这类确定性错误用脚本或 Action 直接修，不用代理；真实测试失败才派代理读 CI 日志修，**最多 5 次**，超过就关闭。

### 7. 质量三层防线（9:44–10:50）
代理会为了让 CI 变绿走捷径：改生产代码、改/删/静默已有测试、在测试里加长 wait。按顺序设防：
1. **确定性规则**：PR 改了测试、mock、fake、stub 以外的任何文件就直接关闭。
2. **先处理 AI 代码评审的 P0 评论**：在人看到前，让代理解决评审 bot 的最高优先级评论。
3. **专用 LLM 评审代理（LLM-as-a-judge）**：读 diff，遇到上述捷径就拒绝，并写明理由；检查项随经验增加（讲者称审过的 PR 中拒绝了 73 个，总数字幕听不清）。

### 8. 让代理环境和 CI 对齐（9:03–9:44）
- 代理开 PR 前应能在本地构建和 lint。Duolingo 起初在 Linux 上跑 iOS 代理，PR 开出 20–30 分钟后才在 lint 上失败，62% 的 lint 失败来自两条规则。
- 分层修：prompt 加示例 → CI 自动修 lint → 删除信号不强的 lint 规则 → **把代理迁到与 CI 相同的运行环境**（讲者称这一步是「真正的修复」）。

### 9. 给新代码开入口（8:40–9:03）
- 工程师给自己的 PR 加一个 label，复用同一流水线；跳过 selector，直接用该 PR 的文件；代理产出一个链接回原 PR 的 draft PR。

### 10. 回写反馈并跟踪指标
- 定期读 judge 拒绝理由和审阅反馈，更新 prompt 与 testing skill。
- 跟踪：分层与整体覆盖率、合并数、拒绝数、代理在新增测试中的占比、每次运行成本。
- 讲者的解读：代理占比下降而工程师自写测试变多，是好事（10:50–11:35，因果未验证）。

## A 部分交付物

- 一份范围与基线文档；
- 仓库内的 testing skill / 规则文件；
- selector 脚本、backfill 定时流程、PR 状态机、label 触发流程；
- 三层质量防线的规则与 judge 提示词；
- 一张指标看板。

## A 部分验收清单

- [ ] 每个代理 PR 都标明 AI 生成，且必须人审批才合并
- [ ] 改了非测试文件的 PR 会被自动关闭
- [ ] judge 会拒绝改/删/静默测试和长 wait，并写理由
- [ ] 同一文件不会被重复开工；被拒文件有冷却期
- [ ] CI 修复有次数上限
- [ ] 代理能在开 PR 前本地构建和 lint
- [ ] 覆盖率口径分清「切片」和「整体」，不混报

## A 部分易误解点

- 「代理写并合并」不等于无人参与：每个 PR 都经人审批。
- Duolingo 的 59% 只指 MVVM 切片，整体是 11% → 24%（约 8 个月）。
- 225,000 行是测试代码行数，不等于测试质量；讲者没有给缺陷拦截率或 flaky 率。
- 本地验证约 50% 的合并率是正常的摸底结果。
- 很多问题出在代码库本身（难 mock 的单例、无效 lint 规则），改代码库对人和代理都有好处。

## A 部分示例走查（不同于原视频）

一个 Python 后端仓库，pytest 覆盖率 18%：切片选 `services/` 和 `repositories/`，跳过 Django 视图；selector 给这两类加权、给超过 800 行的文件扣分；代理只允许改 `tests/` 和 `conftest.py`；状态机用 GitHub Actions 定时任务实现；judge 拒绝修改 `src/` 或加 `time.sleep` 的 PR。

- lint 失败比例（字幕 “30 13.6%”）。
- 新代码入口用的 label 确切名称。

# B 部分：维护一个由代理持续改动的系统

来源：[Agents Made Code Free. Maintaining It Didn't Get Cheaper.](https://www.youtube.com/watch?v=oeknLUsN_GE)，依据为英文自动字幕，**未核验画面**。讲稿是逐张幻灯片的旁白，很多图示（五道墙、gauges、周流程图、18 个问题）只在画面上，下文只写字幕能确认的部分。讲者用 Thanos 和六颗宝石作隐喻，这里改写成直白的问题。数字均为讲者口述。

## 前提判断（0:00–1:31）

- 代理让代码便宜，也让**混乱更便宜**。一次性大删大重写会丢掉有用的东西，而且代理继续写，混乱会长回来。
- 目标：承认「变更多到没人能逐个检查」这条线，用**每周小清扫 + 系统内建的反馈回路**待在线以下，而不是周期性推倒重来。

## 需要的输入

| 输入 | 说明 |
|---|---|
| 系统的 slice 划分 | 一个任务落在哪个切片（讲者：一个国家 × 一个流程，110 国、约 1 万个场景） |
| prose 指令清单 | 系统里写给代理的自然语言指令（讲者估计占系统约 3/4） |
| 领域专家 | 能为决策签字的人 |
| 运行记录 | traces、日志、历史会话，可回放的真实任务 |
| ledger（台账） | 记录每次改动、lint 结果、反馈、删除理由的文件 |

## 步骤

### B1. 划 slice，限定改动落点（1:34–4:53）
- 每个改动默认只留在自己的 slice 里，跨 slice 需要明确理由。

### B2. 把 prose 当代码来测
- **变异测试**：故意改坏一句 prose，看有没有测试变红。讲者的结果是几乎都不红，说明 prose 主要靠人守护。
- 给 prose 做「编译器」和 lint（讲者自建，工具未公开），每个改动过的文件 lint 后记入 ledger。
- 避免「不要调用 X」这类反向写法：它会让模型知道 X 存在。

### B3. 一份文档，两类读者
- 代理读精确的结构化 block，专家读 block 周围的说明并签字。**不维护第二份副本**，副本会漂移。代码也要配专家看得懂的描述。
- 专家按「代理当时看到的样子」审单个任务，批注变成代理的下一次改动，并在同一任务上复测。记录每个结果被接受还是被拒绝，用准确率找出人还需要看的地方。

### B4. 决定什么写成代码、什么留在 prose（4:56–7:26）
- 观察 **walk**（代理穿过 prose 的路径）。只有**反复出现且跨 slice 一致**的路径才固化为代码 workflow，并删掉对应的 prose。
- 踩坑：prose 里还写着工具内部步骤名时，代理会把步骤再执行一遍。**prose 只保留决策**，不写工具内部步骤。
- 决策表分工：**代码准备事实并执行；专家拥有决策表；模型只挑一行；没有合适的行就转人工。**
- 边界是双向的：专家看不懂的代码表达式可以挪回 prose（讲者挪回过几百行）。
- 案例：prose 写限额 1,500、代码写 1,000，同一订单两处结果不同，且不报错。这就是两份副本漂移。

### B5. 控制从「模型看到什么」开始（7:26–9:17）
- 由 runtime 决定模型看到哪些事实，给最小上下文；大数据集用 handle 引用，写入前由 runtime 校验 handle 与上下文一致。
- **写路径只由代码打开**：写入前多道检查（讲者说五道，具体内容只在画面上），写入后校验是否真正落地，用 journal 保证重试只执行一次。

### B6. 保护人的注意力
- **把自己当第一个 gauge**：累到说不清改了什么，就先停下来修流程，不等 dashboard 变红。
- 上线新检查前，把规则回放到历史会话上估算 **blast radius**（讲者：几千个会话，触发率不到 1%），数字跳变处由人去读。
- 信号处理：单个信号等它复现；跨 slice 聚集的问题修背后的概念；专家批注转成 eval，让代理去兄弟 slice 搜同类失败，只修确认失败的。
- 反过拟合：定期剥掉代理为通过当天任务加的条件，看 eval 掉多少，得到缺口清单。

### B7. 验证纪律
- 真实任务回放优先；先写下什么结果会证伪；新检查先故意失败一次。
- 冻结真实任务集，用旧版本对新版本回放。
- **重构后核对每个分支恰好落地一次**。讲者案例：重构丢了「金额超限」分支，订单会绕过 team lead 审批。
- 没有真实任务走过的分支标为「无证据」。
- 第二个代理按 checklist 独立复核，不给它作者的推理；它也可能被说服。
- 用 ledger 核对批次完整性，代理可能悄悄跳过批次尾部。

### B8. 文件化记忆与反馈
- 记忆分两份：「发生过什么」和「现在什么是真的」，新会话从后者开始。每个 issue 连到根因，无证据不行动。
- 给每个用户反馈入口，回路直接写入 ledger，不经过你本人中转。

### B9. 每周清扫
- **Ratchet gauges**：计数只许下降（讲者运行 2 个，另 6 个计划中）。
- 由真实使用决定保留什么；删除前写明名字和证据；变体退役时，它的测试一起退役。
- 回看偏见：系统的 skills 和记忆是否只复制了你一个人的习惯。

## B 部分验收清单

- [ ] 每个改动都标明所属 slice，跨 slice 有理由
- [ ] prose 做过变异测试，改动文件都 lint 并入 ledger
- [ ] 同一规则只有一份来源，没有 prose 和代码各写一份
- [ ] 写入只能经代码路径，有写后校验和幂等 journal
- [ ] 新检查上线前做过历史回放，知道 blast radius
- [ ] 重构后逐分支核对，未覆盖分支标「无证据」
- [ ] 每周有一次小清扫，gauges 只降不升，删除有证据

## 两部分怎样配合

- A 的「三层防线」「CI 修复上限」「反馈回写」可以直接作为 B7 验证纪律在代码 PR 上的落地。
- B 的「每周清扫」「ratchet gauges」「删除附证据」可以用来管理 A 产出的大量测试，避免测试本身变成新的混乱。
