# 用编码代理批量补写单元测试

来源：Duolingo 的 Kush（标题署名 Kush Agrawal）在 AI Engineer 的演讲 [225,000 Lines of Tests, Written and Merged by Agents](https://www.youtube.com/watch?v=D_4Rn6uLdQM)（12:38）。依据为英文自动字幕，**未核验画面**。时间戳为字幕时间。下文的数字是讲者在 Duolingo iOS 上报的结果，不是保证值；标「可采用」的是整理时补充的建议。

## 什么时候用

- 代码库覆盖率低，想用编码代理批量补测试，但每个 PR 仍要人审批。
- 已有一类「形状相同」的批量改造任务（迁移架构、换异步框架、补 snapshot test），想复用同一闭环（讲者 11:36 起提到 Duolingo 已这样用）。

不适合：没有 CI、没有覆盖率报告、或团队不愿审代理 PR 的仓库，先补这些前置条件。

## 需要的输入

| 输入 | 说明 |
|---|---|
| 目标仓库与语言/测试框架 | 例：iOS + XCTest/Swift Testing；Android + JUnit；Python + pytest |
| 可测切片 | 架构上最容易测的部分（Duolingo 只做 MVVM 的 view model / repository / data source，跳过 UI） |
| 覆盖率报告来源 | 每次合并到主分支自动生成并存到共享位置 |
| 编码代理 | 能在云端/CI 运行的代理（他们用 Claude Code） |
| 编排引擎 | 支持定时、子流程、重试、超时、幂等（他们用 Temporal；可采用其他 durable workflow 引擎或 CI 定时任务） |
| 代码托管 | 支持 label、PR、auto-merge、Actions 的平台（他们用 GitHub） |
| 可观测 | 能看每次代理运行的状态与成本（他们用 Datadog） |

## 核心循环

`identify → write → verify → resolve → iterate`（2:28）：选文件 → 代理写测试 → CI 与质量验证 → 人审合并 → 把拒绝理由回写进 prompt 和 skill。

## 步骤

### 1. 记录基线，圈定切片
- 记录整体覆盖率和各层覆盖率（Duolingo 起点：整体 11%，MVVM 约 9%，0:01–1:43）。
- 只选最好测的切片作为第一阶段范围。
- 成功标准：有一份写明范围和基线数字的文档。

### 2. 本地小批验证（4:03–5:19）
- 用一个代理命令当编排者：生成覆盖率报告 → 用脚本选文件 → 每个文件派一个子代理写测试、一个子代理开 PR。
- 分小批跑（他们两批：17 个合并 8 个，40 个合并 19 个）。**目标是收集失败模式，不是追求合并数。**
- 把每种失败写进仓库里的 testing skill / 规则文件。讲者遇到的例子：
  - 同一文件混用两种测试框架 → 写明何时用哪种；
  - 难以 mock 的具体类单例 → 改代码库为协议/接口版本，再加 lint 强制；
  - 并发和依赖时间的测试导致 flaky → 在 skill 里补规则与示例。
- 成功标准：主要失败模式都有对应规则或代码改造。

### 3. 建立覆盖率的唯一来源
- 每次合并到主分支触发一个 CI job，生成覆盖率报告并上传共享存储（他们用 S3，5:21 起）。

### 4. 写 selector 打分（5:21–7:21）
- 给每个源文件打「代理有多大把握写好测试」的分：
  - 目标文件类型加权（他们给 view model / repository / data source **2.5 倍**）；
  - 遗留代码降权；
  - UI 暂时跳过（更适合 snapshot test）；
  - 大文件扣分。
- 成功标准：每批选出的文件以高把握度文件为主。

### 5. 定时 backfill，并行写测试
- 定时任务拉最新覆盖率 → selector 选一批 → 每个文件一个子流程并行执行。
- 代理每次：克隆仓库 → 读仓库内 testing skill → 只写测试和必要的 mock/fake → 开 PR。
- PR 打统一 label（他们用 generated test），描述用统一模板并**写明 AI 生成**。
- 审阅人有四个选项：批准即自动合并、直接 push 修改、改派、关闭并写理由。
- 利用编排引擎的幂等，保证同一文件不会被重复开工。

### 6. PR 生命周期状态机（7:21–8:40）
每隔几小时巡检所有带该 label 的开着的 PR，**每个 PR 每轮只做一个动作**：

| 状态 | 动作 |
|---|---|
| 有冲突，或已开约 3 周 | 关闭，标 stale |
| CI 运行中，或已有审阅人 | 跳过 |
| CI 绿且无审阅人 | 用 `git blame` 找被测源文件主要贡献者，指派并开 auto-merge |
| CI 红 | 进入修复（见下） |
| 被审阅人拒绝 | 该文件冷却 30 天 |

CI 修复分层：pre-commit / lint 这类确定性错误用脚本或 Action 直接修，不用代理；真实测试失败才派代理读 CI 日志修，**最多 5 次**，超过就关闭。

### 7. 质量三层防线（9:44–10:50）
代理会为了让 CI 变绿走捷径：改生产代码、改/删/静默已有测试、在测试里加长 wait。按顺序设防：
1. **确定性规则**：PR 改了测试、mock、fake、stub 以外的任何文件就直接关闭。
2. **先处理 AI 代码评审的 P0 评论**：在人看到前，让代理解决评审 bot 的最高优先级评论。
3. **专用 LLM 评审代理（LLM-as-a-judge）**：读 diff，遇到上述捷径就拒绝，并写明理由；检查项随经验增加（讲者称审过的 PR 中拒绝了 73 个，总数字幕听不清）。

### 8. 让代理环境和 CI 对齐（9:03–9:44）
- 代理开 PR 前应能在本地构建和 lint。Duolingo 起初在 Linux 上跑 iOS 代理，PR 开出 20–30 分钟后才在 lint 上失败，62% 的 lint 失败来自两条规则。
- 分层修：prompt 加示例 → CI 自动修 lint → 删除信号不强的 lint 规则 → **把代理迁到与 CI 相同的运行环境**（讲者称这一步是「真正的修复」）。

### 9. 给新代码开入口（8:40–9:03）
- 工程师给自己的 PR 加一个 label，复用同一流水线；跳过 selector，直接用该 PR 的文件；代理产出一个链接回原 PR 的 draft PR。

### 10. 回写反馈并跟踪指标
- 定期读 judge 拒绝理由和审阅反馈，更新 prompt 与 testing skill。
- 跟踪：分层与整体覆盖率、合并数、拒绝数、代理在新增测试中的占比、每次运行成本。
- 讲者的解读：代理占比下降而工程师自写测试变多，是好事（10:50–11:35，因果未验证）。

## 交付物

- 一份范围与基线文档；
- 仓库内的 testing skill / 规则文件；
- selector 脚本、backfill 定时流程、PR 状态机、label 触发流程；
- 三层质量防线的规则与 judge 提示词；
- 一张指标看板。

## 验收清单

- [ ] 每个代理 PR 都标明 AI 生成，且必须人审批才合并
- [ ] 改了非测试文件的 PR 会被自动关闭
- [ ] judge 会拒绝改/删/静默测试和长 wait，并写理由
- [ ] 同一文件不会被重复开工；被拒文件有冷却期
- [ ] CI 修复有次数上限
- [ ] 代理能在开 PR 前本地构建和 lint
- [ ] 覆盖率口径分清「切片」和「整体」，不混报

## 易误解点

- 「代理写并合并」不等于无人参与：每个 PR 都经人审批。
- Duolingo 的 59% 只指 MVVM 切片，整体是 11% → 24%（约 8 个月）。
- 225,000 行是测试代码行数，不等于测试质量；讲者没有给缺陷拦截率或 flaky 率。
- 本地验证约 50% 的合并率是正常的摸底结果。
- 很多问题出在代码库本身（难 mock 的单例、无效 lint 规则），改代码库对人和代理都有好处。

## 示例走查（不同于原视频）

一个 Python 后端仓库，pytest 覆盖率 18%：切片选 `services/` 和 `repositories/`，跳过 Django 视图；selector 给这两类加权、给超过 800 行的文件扣分；代理只允许改 `tests/` 和 `conftest.py`；状态机用 GitHub Actions 定时任务实现；judge 拒绝修改 `src/` 或加 `time.sleep` 的 PR。
