# 把代理环境做成可信任的代码库

在仓库里使用 AI coding agents（AI 编程代理）时，按本 skill 行事：先改造代理所处的环境，再指望产出可合并。目标不是接受 slop（劣质/灌水代码），而是用可强制执行的约束，让代理默认做对的事。

本 skill 的方法来自一场演讲中的实践，不是普遍已证实的保证。标注为「讲者实践」的条目，是 Lauren Tan 对其团队做法的描述，移植时要按当前仓库取舍，不要原样照搬极端规则（例如禁止约 99% 的注释，或自动合并大多数 PR）。标注为「整理推论」的步骤，是为了让方法可执行而补充的操作顺序，演讲原文并未逐步规定。

## 1. 核心原则

- **信任，但不是盲目信任。** 投资于代理的环境，使你能相信它们会做对的事；不要在没有约束时假设「生成出来就能合」。
- **把约束写进代码和确定性检查，而不是只写进散文。** 优先使用 API 设计、架构、重构、lint rules（代码检查规则）、类型系统、编译器和测试。`rules`、`skills`、`agents.md` 只覆盖真正需要判断的部分。
- **每次纠正代理，都优先变成可复现的检查。** 不要只在注释或 `agents.md` 里加一句「下次别这样」——注释会过时、常常没人读，而且不可强制执行；代理还可能把注释当成「这次没做对」的辩护，或把一次小纠正当成永远不能打破的硬规则（over-rotate）。
- **软件工程师的元工作：** 在大幅提高产能的同时，维持甚至提高代码质量。有人把高吞吐流水线叫 software factory（软件工厂）；先把内层质量做扎实，再谈外层自动化。

## 2. 倒金字塔：投入优先级

按这座 inverse pyramid（倒金字塔）安排时间。越往下越应优先投入；上层不能代替下层。

1. **确定性层 A — 用代码本身约束：API、架构、重构。**  
   把「正确用法」做成默认路径，把错误用法做成难以触及或根本写不出来。对要用好就需要 nuance（分寸）的 API，考虑收窄或在产品代码中禁止，只留在受控封装里。

2. **确定性层 B — lint、类型系统、编译器、测试。**  
   与上一层一起使用，强制代理默认做对。lint 报错应指出 root cause（根因），而不是允许再打一个补丁。

3. **验证层 — runtime verification（运行时验证）与 formal verification（形式化验证）。**  
   用来找 bug、检查希望始终成立的性质与 invariants（不变量），并判断代理是否理解了目标和意图。

4. **少量散文层 — rules、skills、`agents.md`。**  
   只放需要判断、无法写成确定性检查的说明。这是最后一层，不是第一反应。

两层确定性约束一起用，目的是限制代理能做的事，并迫使它们「默认就做对」。验证是叠加上去的工具，不是银弹。散文规则不可替代前几层。

## 3. 纠正决策流程

每当代理犯错、或你想纠正一种行为时，按这次序做，不要先改 `agents.md`。

1. **描述这次错误。** 代理做了什么？希望它做什么？这是一次性走神，还是会重复出现的模式？
2. **先问能否做成 API 或架构改动。** 能否用更好的封装、目录边界或默认 API，把这类问题按类别消灭，使产品代码里再也写不出这种用法？
3. **若不能，再问能否做成确定性检查：** lint rule、类型、编译器检查，或测试（包括属性测试）。新的反模式要拦住，仓库里已有的旧实例也要清理，否则下一轮代理会把旧代码当成惯例复制。
4. **再问能否用验证接住：** 让代理自己跑程序、用调试工具、对照 feature map（功能地图）、查看录像/截图/图示，或对关键流程与算法做形式化检查。
5. **只有当前几步都做不到，或确实需要判断时，才写入 rules / skills / `agents.md`。** 写的时候避免变成不可强制的禁令清单；不要给代理一个「用散文解释为什么这次可以例外」的逃逸口。
6. **「整理推论」：** 记录这条新约束属于倒金字塔的哪一层、覆盖哪种错误、以及如何验证它真的拦住了问题。不要把一次个案写成永远不可打破的硬规则。

## 4. 代码库是最大输入（花园比喻）

代理的输出取决于输入，而代码库往往是最大的输入之一。权宜之计、anti-patterns（反模式）、已废弃代码和技术债务，很容易被下一个代理当成「这里就是这么写的」而复制，如同园子里的杂草扩散。

约束和护栏像混凝土地基，新代码会绕着它生长。要把代码库尽量保持干净，让代理总是复制好的模式。

因此：

- 发现坏模式时，同时处理「不再新增」和「清理已有」。
- 审查时代理写出的变通写法，不要只在这一个 PR 里改掉就结束；问它会不会成为下一轮的输入。
- 「整理推论」：清理时应保留或写出一个清晰的正确范例，否则代理可能只学会「不要那样」，却不知道该怎样。

## 5. 具体模式（均为讲者实践，当作示例）

以下是讲者团队的做法，用来说明倒金字塔如何落地。不要把某一条当成必须在所有仓库执行的命令。

### 5.1 用框架禁掉需要分寸的 API

凡是要用好就需要 nuance 的东西，往往会导致 slop；代理不擅长这类 API。例子：React 的 `useEffect` 有适用场景，但经常被误用。

**讲者实践：** 在产品代码里禁止 `useEffect`，只允许在 Dune 框架的部分 API 内部使用，从而按类别消灭这类审查负担。Dune 是他们为 Grok Bot 做的客户端框架，讲者把它比作「给 Electron 应用的 Next.js」，价值主要在内建约束和 lint，而不在技术新奇。

**整理推论：** 在其他技术栈中，先找出代理反复用错、且人类也常误用的 API，考虑收窄到受控封装，而不是在散文里反复提醒「请谨慎使用」。

### 5.2 用目录和依赖规则表达不可跨越的边界

**讲者实践：** 他们观察到代理常把 Electron 的 main thread（主进程）代码导入 renderer thread（渲染进程），造成长任务和 jank（卡顿）。做法是用两个顶层目录（讲者所述为 Electron renderer 与 Electron main），并用 dependency graph analyzer（依赖图分析器）和 lint 禁止彼此导入。

**整理推论：** 对任何「这两类代码不能混用」的边界（进程、层、权限、同步/异步），优先用目录约定加可强制的依赖规则，而不是口头提醒。

### 5.3 不要用注释为补丁辩护；用 lint 指向根因

**讲者实践：** 代理会利用 Markdown（文档、注释、rules、skills）为「没做对的事」写理由。一个例子是大量使用 `setTimeout`、`requestAnimationFrame`、`requestIdleCallback` 当作快速修补，掩盖 VS Code 命令式风格与 React 声明式风格之间的架构冲突；代理还写注释为这种做法辩护，计时器随后扩散，并可能因频繁创建销毁而加重垃圾回收和卡顿。

他们因此禁止约 99% 的注释（注释易过时、人也不爱读、不可强制，还给代理逃逸口），改用带有明确、有帮助报错的 lint，要求代理修根因而不是绕过去。

这是他们较极端的取舍，不是行业标准。若采用类似策略，应先约定哪些注释仍然允许（例如公开 API 的必要说明），再禁掉作为「这次可以例外」的辩护文字。

### 5.4 运行时验证：feature map、可复用 CLI、验证产物

**讲者实践：**

- 给代理自己跑代码的途径，并使用人类也会用的调试工具，例如 Chrome DevTools Protocol。
- 在 runtime verification 的 skills 里放一份 feature map：从用户视角列出应用功能的「站点地图」，提供共享词汇，避免「左边栏那个东西」让代理猜测。
- 把自定义 CLI 和 driver（驱动）放进 skill，让代理每次复用同一套接口，减少 token，且可测试。
- 代码审查更多转向看 verification artifacts（验证产物）：录像、截图、图示、形式化结果。前提是验证体系足够强；不能由此推出可以完全不看代码。

他们还提到用 pstack（讲者又称 potato stack）里名为 state chart 的 skill，从用户视角把状态机可视化，便于和视频、截图一起审。

### 5.5 形式化验证与 UI 属性测试（不是银弹）

**讲者实践：**

- 用 **TLA+** 对重要用户流程做 model checking（模型检测），例如跨多设备、多平台的通知。
- 用 **Lean** 证明某些算法性质，例如自研 virtualization（列表虚拟滚动）库不应出现 flickering（闪烁）或 jittering（抖动）。
- 用 property-based testing（基于性质的测试）检查 UI；自动字幕称使用名为 **Bombadil** 的库（名称仅来自自动字幕，未经核验，不要把该拼写当成已确认的官方名称）。
- 形式化验证已帮他们找到 bug，看起来有前途，但「certainly not a silver bullet」，只是环境中的又一层工具，整体仍在实验。

**整理推论：** 优先把形式化方法用在「必须成立」的流程与算法不变量上，而不是试图证明整个应用。

### 5.6 把 token 花在验证上

讲者转述：有人（Cindy）在不信任代理、因微妙 bug 被合入之后，把验证补上；后来其日常 token 大部分用于验证。讲者称自己的观察类似。具体比例是转述/自我观察，不要当成必须达到的指标。

要点是：信任缺口要用验证补，而不是只生成更多代码。许多验证技法本身并不新，只是以前可能因难写、难维护而用得少；代理降低了书写与维护成本，可以把测试做到从前在经济上不合理的深度。形式化验证也有助于思考产品应如何工作，以及代理是否真的理解意图。

## 6. 警告：先打地基，再谈软件工厂

- **不要在内层编码循环还在产 slop 时，先自动化 outer loop（外层循环）。** 若 inner coding loop（内层编码循环）本身产出 slop，自动化只会产出更多 slop，并不断消耗更多 token。先改善代码库、静态分析和验证，这些本就是自动化的前提。
- **形式化验证不是银弹。** 把它当作附加层，不要当作全部保障。
- **自动合并、产品代码「不必深入人工审查」是讲者对其当前代码库质量的判断，不是可以照搬的安全保证。** 地基不够时不要模仿自动合入。
- 讲者提到的产量、回滚率、发版频率和性能对比，都是现场主张，口径未在演讲中给出，**不要当作本 skill 的目标数字或已核实事实。**

讲者描述的外层例子（仅供理解「地基之后才做什么」）：准备好之后，可用编排工具拉起 Cursor、cloud agents 等，例如在发新版本后对应用做 fuzz（模糊测试）、像真实用户一样操作以找 bug，再开修复 PR。在约束和验证尚未可靠之前，不要把这个外层当作起点。

## 7. 仓库审计清单

对当前仓库逐项检查。能做成确定性检查的，就不要停在「写进文档」。

**倒金字塔与优先级**

- [ ] 纠正代理的默认动作，是先改 API/架构或 lint/类型/测试，而不是先改 `agents.md` 或加注释。
- [ ] `agents.md`、rules、skills 只保留需要判断的内容；其中若存在「不要再犯 X」却没有任何强制检查，应下沉到确定性层。

**代码库作为输入**

- [ ] 已识别代理可能复制的坏输入：权宜之计、反模式、废弃 API、技术债务、辩解性注释。
- [ ] 对每类坏模式：既有 lint/测试拦住新增，也有清理或隔离旧实例的计划。
- [ ] 「整理推论」：仓库里至少有一处清晰的正确范例，可被当作复制对象。

**架构与边界**

- [ ] 需要分寸才能用对、且代理反复用错的 API，是否已收窄或在产品代码中禁止，只留在受控封装中。
- [ ] 不可混用的边界（如进程、层级）是否由目录结构和依赖/lint 规则强制，而不是只写在说明里。
- [ ] 是否存在用 `setTimeout`、`requestAnimationFrame`、`requestIdleCallback` 等计时器掩盖架构问题的补丁；若有，应修根因并拦住回归。

**lint 与注释**

- [ ] 关键约束的报错会告诉代理修根因，而不是暗示可以再打补丁。
- [ ] 注释和 Markdown 没有成为「这次可以不遵守规则」的逃逸口。（是否像讲者那样禁止绝大多数注释，由团队自行决定。）

**验证**

- [ ] 代理能自己运行程序，并能使用与人类开发者相同的关键调试途径（若适用，例如 Chrome DevTools Protocol）。
- [ ] 有一份从用户视角出发的 feature map，或等价的共享词汇，减少含糊指示。
- [ ] 重复的验证步骤被收成可复用、可测试的 CLI 或 skill，而不是每次靠代理现写脚本。
- [ ] 审查时能看到录像、截图、图示或形式化结果等验证产物；关键用户流程和关键算法的不变量有对应检查（测试、模型检测或定理证明，按风险选择）。
- [ ] 形式化方法被当作附加层，没有被当成唯一保障。

**自动化门槛**

- [ ] 在搭建 software factory 或自动开 PR / 自动合并之前，已确认内层循环不会稳定产出 slop。
- [ ] 尚未把讲者的团队数字当成自动化已经「足够安全」的依据。

## 8. lint 报错文案模板

报错应说明禁止什么、为什么、以及应修的根因。不要写完整的 lint 插件代码。下面是一条示例字符串，主题取自演讲中的计时器补丁，可按实际规则改写：

```
Do not use setTimeout, requestAnimationFrame, or requestIdleCallback to patch over a timing or architecture problem.
This usually hides a clash between an imperative update style and a declarative UI, and the workaround will get copied by later agents.
Fix the root cause in the data or update flow so the UI can render correctly without a timer.
```

「整理推论」：好的报错应同时做到三点——点名被禁的写法、说明它为何有害（含「会被后续代理复制」）、给出正确方向。避免只写 `Don't do this`。
